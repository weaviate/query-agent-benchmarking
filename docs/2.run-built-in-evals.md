# 2. Run Built-in Evals

## Search Evaluation

### Run a Single Search Eval

```python
import query_agent_benchmarking

# reads parameters from default config (benchmark-config.yml)
query_agent_benchmarking.run_search_eval()

# pass in override params
query_agent_benchmarking.run_search_eval(
    dataset="bright/psychology",
    agent_name="query-agent-search-only",
)
```

### Run Multiple Search Evals

Compare multiple agents on the same dataset:

```python
import query_agent_benchmarking

query_agent_benchmarking.run_search_evals(
    dataset="bright/psychology",
    agent_names=["hybrid-search", "query-agent-search-only"],
)
```

### `run_search_eval()` Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `config_path` | `str` | Built-in config | Path to YAML config file |
| `dataset` | `str` | Config value | Built-in dataset name (e.g., `"beir/scifact/test"`, `"freshstack-langchain"`) |
| `docs_collection` | `DocsCollection` | `None` | Custom document collection (see [Custom Evals](3.run-custom-evals.md)) |
| `queries` | `QueriesCollection \| list[InMemoryQuery]` | `None` | Custom queries (see [Custom Evals](3.run-custom-evals.md)) |
| `agent_name` | `str` | Config value | `"query-agent-search-only"`, `"hybrid-search"`, or `"external_service"` |
| `num_trials` | `int` | `1` | Number of evaluation trials |
| `use_subset` | `bool` | `True` | Whether to use a random subset of queries |
| `num_samples` | `int` | `50` | Number of samples if `use_subset` is True |
| `batch_size` | `int` | `5` | Batch size for async processing |
| `max_concurrent` | `int` | `5` | Max concurrent requests for async |
| `use_async` | `bool` | `True` | Whether to use async execution |
| `agents_host` | `str` | Config value | Host URL for the Weaviate agents service |
| `external_service_host` | `str` | Config value | Host URL for external service mode |
| `output_path` | `str` | Auto-generated | Path to save results |
| `random_seed` | `int` | `None` | Random seed for reproducibility |
| `embedding_model` | `str` | Config value | Embedding model to use |

`run_search_evals()` accepts the same parameters, except it uses `agent_names` (str or list of str) instead of `agent_name`.

Results are saved to JSON files by default and returned as a dict of aggregated metrics.

## Ask Evaluation

### Run an Ask Eval

```python
import query_agent_benchmarking

# reads parameters from default config
query_agent_benchmarking.run_ask_eval()

# pass in override params
query_agent_benchmarking.run_ask_eval(
    queries="multihoprag",
    dataset="multihoprag",
    agent_name="query-agent-ask",
)
```

### `run_ask_eval()` Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `queries` | `str \| AskQueriesCollection \| list[InMemoryAskQuery]` | Config value | Built-in dataset name, custom collection, or list of query objects |
| `config_path` | `str` | Built-in config | Path to YAML config file |
| `dataset` | `str` | Config value | Built-in dataset name for agent initialization |
| `docs_collection` | `DocsCollection` | `None` | Custom document collection |
| `agent_name` | `str` | Config value | `"query-agent-ask"` or `"external"` |
| `judge_model` | `str` | `"openai/gpt-4.1"` | LLM model for the judge |
| `ensemble_k` | `int` | `3` | Number of ensemble votes for judge |
| `num_trials` | `int` | `1` | Number of evaluation trials |
| `use_subset` | `bool` | `True` | Whether to use a random subset of queries |
| `num_samples` | `int` | `50` | Number of samples if `use_subset` is True |
| `batch_size` | `int` | `5` | Batch size for async processing |
| `max_concurrent` | `int` | `5` | Max concurrent requests for async |
| `use_async` | `bool` | `True` | Whether to use async execution |
| `agents_host` | `str` | Config value | Host URL for the agents service |
| `external_service_host` | `str` | Config value | Host URL for external service mode |
| `sleep_between_requests` | `float` | `0` | Seconds to sleep between requests (sync mode, for rate limiting) |
| `output_path` | `str` | Auto-generated | Path to save results |
| `random_seed` | `int` | `None` | Random seed for reproducibility |
| `embedding_model` | `str` | Config value | Embedding model to use |

### Ask Evaluation Scoring

- Most datasets use an **LLM-as-judge** (DSPy ensemble voting) to evaluate semantic alignment between the generated answer and ground truth.
- **MultiHop-RAG** uses **exact match** accuracy instead, since its ground-truth answers are short constrained values.

## Pre-Built Benchmarks

### BEIR

Published by Thakur et al. in 2021, BEIR was designed to evaluate the out-of-distribution generalization capabilities of retrieval systems. We focused on 3 subsets: Natural Questions (3,452 queries), SciFact (300 queries), and FiQA (648 queries). Natural Questions presents a large-scale retrieval challenge with 2.7 million documents, whereas SciFact and FiQA are smaller scale corpora focused on particular domains such as scientific papers and financial questions, respectively.

### LoTTe

Similarly to BEIR, LoTTe, short for, Long-Tailed Topic-stratified Evaluation, was developed to test how well search systems can generalize to particular domains. LoTTe interestingly uses natural search queries from Google, via GooAQ) mapped to StackExchange answers. Each benchmark in LoTTe contains two query sets, "search" and "forum": "search" queries are derived from Google autocomplete, and "forum" queries are derived from StackExchange post titles. There are 2002 and 661 "forum" and "search" queries in LoTTe Lifestyle, respectively. There are 2002 and 924 "forum" and "search" queries in LoTTe Recreation, respectively.

### BRIGHT

BRIGHT was introduced by Su et al. as a testbed for level 3 retrieval. While level 1 is keyword search and level 2 is semantic search, level 3 represents the frontier: reasoning-intensive retrieval. Unlike the other benchmarks we included, BRIGHT's queries are long and descriptive. Sampled from user posts on StackExchange, each query is paired with gold documents sourced from external web pages cited in accepted or highly upvoted answers. There are 103, 116, 103, 101, and 101 queries in the respective Biology, Earth Science, Economics, Psychology, and Robotics subsets we test with. They further contain average query lengths of 115, 109, 182, 150, and 819 tokens, respectively. These query lengths highlight how BRIGHT forces retrieval systems to go beyond surface matching and utilize complex reasoning to find relevant search results.

### EnronQA

EnronQA uniquely addresses the challenge of retrieval over private corpora – 103,638 emails across 150 distinct user inboxes from the Enron corpus. We run our tests with a sample of 500 queries from the largest user inbox, dasovich-j. EnronQA uses synthetic queries derived from these emails. This is an interesting emerging technique for benchmarking information retrieval without having to manually annotate queries and their gold documents. For those interested, we have a recipe here showing how you can achieve this with the Weaviate Transformation Agent.

### WixQA

Wix.com is a website building and hosting platform serving millions of users who encounter technical challenges ranging from domain configuration, payment processing, or design customization, to give a few examples. We use the Expert Written queries, containing 200 customer queries submitted through Wix support channels. Each of these questions are paired with comprehensive answers and gold documents manually authored by Wix support specialists.

### MultiHop-RAG

The MultiHop-RAG benchmark (Tang and Yang, 2024) evaluates generation quality using accuracy, where each query has a constrained ground-truth answer: entity names for Inference queries (e.g., "YouTube"), "yes" or "no" for Comparison queries, temporal indicators like "before" or "after" for Temporal queries, and "insufficient information" for Null queries. Because these answers are deliberately short, the original paper uses straightforward accuracy — checking whether the model's response matches the ground truth. However, when evaluating systems that produce fuller natural language responses, such as the Weaviate Query Agent, an LLM-as-judge or normalized string matching approach may be more appropriate to determine whether the correct answer is contained within a longer generated response. We adopt exact match accuracy to score Query Agent outputs against the MultiHop-RAG ground-truth answers.
